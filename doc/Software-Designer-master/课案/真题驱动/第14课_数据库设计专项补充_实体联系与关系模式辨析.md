# 第14课 数据库设计专项补充：实体、联系、关系模式与画图判断

## 本课定位

本补充课案用于解决数据库设计下午题中的高频混淆点：实体、联系、属性、关系模式、主键、外键、ER 图菱形联系，以及“是否需要新增实体”的判断。

数据库设计题通常同时考两层模型：

- 概念模型：ER 图，关注业务语义，常见符号是矩形实体、菱形联系、椭圆属性、线端基数。
- 逻辑模型：关系模式，关注表结构，常见形式是 `表名（字段1，字段2，...）`。

失分常见原因是把这两层混在一起：看到联系转换成一张表，就误以为联系在概念模型里必须变成实体。

## 本课目标

- 能区分实体、属性、联系、关系模式。
- 能判断 ER 图中什么时候需要画菱形联系。
- 能判断什么时候属性挂在实体上，什么时候挂在联系上。
- 能判断什么时候需要新增实体，什么时候只需要把联系转换为关系模式。
- 能按软考题面原图风格作答，避免工程建模正确但考试表达不标准。

## 前置知识

### 实体

实体是系统中需要长期记录、能独立区分的一类对象。ER 图中通常画成矩形。

常见判断信号：

- 有独立编号。
- 有自己的名称、状态、属性集合。
- 有相对独立的生命周期。
- 会被其他对象引用。

例如：分公司、部门、员工、客户、商品、订单。

### 属性

属性是描述实体或联系的数据项。

例如：

- 员工的属性：员工号、姓名、岗位、电话、基本工资。
- 部门的属性：部门号、部门名称、电话。
- 某段任职关系的属性：任职时间、任职年限。

属性不一定只属于实体。若属性描述的是两个实体之间的关系本身，就应挂到联系上。

### 联系

联系是实体之间的业务关系。ER 图中常用菱形表示。

例如：

- 分公司设立部门。
- 部门拥有员工。
- 部门由主管管理。
- 分公司由经理管理。

联系不是实体，但联系在逻辑模型转换时可以形成关系模式。

### 关系模式

关系模式是数据库表结构，写作：

```text
表名（字段1，字段2，字段3）
```

关系模式可以由实体转换而来，也可以由联系转换而来。

因此：

```text
概念模型中的实体 -> 可以转换成表
概念模型中的联系 -> 也可以转换成表
```

但“能转换成表”不等于“概念模型中就是实体”。

## 核心考法识别

### 概念模型和逻辑模型不要混用

概念模型回答的是：

```text
业务中有哪些对象？
对象之间有什么关系？
关系的基数是多少？
属性属于谁？
```

逻辑模型回答的是：

```text
要建哪些表？
每张表有哪些字段？
主键是什么？
外键引用谁？
```

软考数据库题常先给 ER 图，再给关系模式空缺。作答时应先补业务语义，再转换成表结构。

### 什么时候画中间菱形

如果题目原图使用矩形实体和菱形联系，且题干要求“补充联系”，标准作答应画菱形。

标准表达：

```text
分公司 1 -- 设立 -- * 部门
部门   1 -- 隶属 -- * 员工
分公司 1 -- 管理 -- 1 经理
部门   1 -- 管理 -- 1 主管
```

不建议在软考答题中改成：

```text
分公司 1 -------- * 部门
```

这种直接连线加基数在某些工程 ER 表示法中可以接受，但若原题使用 Chen 风格 ER 图，缺少联系名和菱形，严格阅卷可能扣分。

做题原则：看原图风格，跟随原图符号。原图有菱形，就继续画菱形。

### 联系加属性后是不是实体

不是。

联系带属性后，仍然可以是概念模型中的联系。例如：

```text
部门 -- 管理 -- 主管
          |
      任职时间
      任职年限
```

这里 `任职时间` 和 `任职年限` 描述的是某主管管理某部门这段关系，不是单独描述部门，也不是单独描述主管。

转换到逻辑模型时，可以形成关系模式：

```text
任职（部门号，主管工号，任职时间，任职年限）
```

这张表是由联系转换来的关系模式，不表示概念模型中必须新增一个“任职实体”。

### 什么时候需要新增实体

优先不新增实体。只有出现下面信号时，才考虑新增实体：

- 有独立编号，例如任职记录编号、投资记录编号、审批单号。
- 有独立生命周期，例如创建、审批、撤销、归档。
- 需要被其他实体引用。
- 需要记录多次明细、流水、历史、批次。
- 原有联系无法区分多次发生。
- 题干明确出现“记录、明细、流水、日志、批次、历史、每次”等业务对象化表达。

如果只是给已有联系增加少量描述属性，通常不新增实体。

## 固定答题步骤

### 第一步：找实体

看题干中“信息包括”前面的对象，以及带编号的对象。

判断句式：

```text
X 信息包括 A、B、C，X 编号唯一标识 X。
```

这类 X 通常是实体。

### 第二步：找属性

题干中“信息包括”后面的内容通常是属性。

例如：

```text
员工信息包括员工号、姓名、隶属部门、岗位、电话和基本工资。
```

对应属性是：

```text
员工号、姓名、隶属部门、岗位、电话、基本工资
```

### 第三步：找联系

题干中的动词或业务关系词通常对应联系：

```text
设立、隶属、管理、负责、拥有、参与、购买、投资、组成
```

### 第四步：定基数

重点抓题干中的数量词：

- 每个、只有一名：通常是 `1`。
- 多个、多名、若干：通常是 `*` 或 `n`。
- 每名员工只能隶属于一个部门：员工端对应一个部门，部门端可对应多名员工，即部门 `1`，员工 `*`。

### 第五步：转关系模式

常用转换规则：

- 实体转换成一张表。
- `1:n` 联系通常在 `n` 端加入 `1` 端主键作为外键。
- `m:n` 联系通常单独转换成一张关系模式。
- 带属性的联系通常单独转换成关系模式。
- `1:1` 联系可以并入任一端，考试通常结合题干关系模式空缺作答。

### 第六步：判断是否新增实体

先问一个问题：

```text
新增信息描述的是一个独立对象，还是描述两个对象之间的一段关系？
```

若描述独立对象，考虑新增实体。

若描述一段关系，优先挂到联系上，再在逻辑模型中转换为关系模式。

## 判分点模板

### ER 图判分点

- 实体是否补全。
- 联系是否补全。
- 联系名称是否符合题干语义。
- 基数是否正确。
- 是否沿用原图符号风格。
- 是否把联系误画成实体。

### 关系模式判分点

- 空缺字段是否正确。
- 主键是否正确。
- 外键是否正确。
- 外键引用对象是否说明清楚。
- 组合主键是否漏写。
- 带属性联系是否正确转换为关系模式。

### 是否新增实体判分点

答题时应明确：

```text
是否需要新增实体：需要 / 不需要。
原因：该信息是独立对象，还是已有联系的属性。
对应关系模式如何调整。
```

不要在正式答题中并列写两套互斥方案。考试题通常按题干最小必要建模给分。

## 常见失分点

- 把关系模式中的“表”误认为 ER 图中必须新增实体。
- 看到“历史、时间、年限”就直接新增实体，没有先判断它是否只是联系属性。
- 原图用菱形联系，作答时改成直接连线，缺少联系名。
- `1:n` 的基数方向反了。
- 把岗位子类当成普通无关实体，忽略它们属于员工分类。
- 外键只写字段名，不说明引用哪个主键。
- 主键和外键混淆。
- 对不确定业务场景写两套互斥答案，导致阅卷认为判断不明确。

## 过关标准

能稳定回答下面 5 个问题，就基本过关：

1. 这个对象有没有独立编号和生命周期？
2. 这个数据项是在描述实体，还是描述联系？
3. 题目原图要求我画菱形联系，还是允许直接连线？
4. 这个联系是 `1:1`、`1:n`，还是 `m:n`？
5. 转成关系模式时，主键和外键分别是什么？

最终记忆句：

```text
概念模型看语义，逻辑模型看表。
联系能变表，但联系不等于实体。
考试画图跟原图风格，原图有菱形就画菱形。
属性能挂已有实体或联系，就不要随便新增实体。
```
